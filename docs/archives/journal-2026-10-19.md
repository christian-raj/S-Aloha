## CMDB augmentée et découverte automatique (CFG-39 à CFG-48)

- **Quoi** : fiche du CI enrichie — identification technique (IP, MAC normalisée, système),
  portefeuille applicatif (CFG-43, CFG-48) et actifs matériels (CFG-44) en colonnes dédiées,
  règles communes au registre et au staging (`CiRules`). Découverte : collecteurs balayage IP
  (ping, ports TCP, DNS inverse, ARP), SNMP v2c (GET encodé en BER, sans dépendance) et Active
  Directory (recherche paginée) ; file d'exécution et planificateur (fréquence, fenêtre en
  heure locale, une tâche à la fois, reprise après arrêt) ; sas de staging avec fusion des
  observations, rapprochement (série 100, MAC 90, nom d'hôte 80, IP 50) limité aux CI
  d'équipement du même périmètre, rapprochement automatique au-delà de 80, conflits motivés,
  Shadow IT (CFG-42) ; coffre AES-256-GCM à clé hors base (CFG-45) ; référentiel des fins de
  support et obsolescence (CFG-47) ; rapport d'inventaire (CFG-39) ; onglet Configuration &
  inventaire du tableau de bord (REP-50 à REP-53) et bloc du sas dans la console. Interface :
  sas de staging (tuiles-filtres, fiche d'un actif avec décision et comparaison), inventaire,
  Paramétrage › Découverte du réseau (tâches, coffre, fins de support), champs conditionnels
  de la fiche CI (`when`, `hint`, intertitres). Migration `CmdbDiscovery`.
- **Pourquoi** : chantier F13. Le code de départ ne compilait pas (API du socle inexistantes)
  et contournait les règles du CI à la réconciliation ; Data Protection sans persistance des
  clés aurait rendu les secrets illisibles à chaque redémarrage du conteneur. Les droits
  suivent le rôle par périmètre (ADR-0014), y compris la lecture du coffre par les
  gestionnaires, sans secret.
- **Fichiers** : `backend/Modules/ServiceConfigurationManagement/` (`Models/CiRules.cs`,
  `Models/DiscoveryEntities.cs`, `Models/Obsolescence.cs`, `Discovery/*`, `Controllers/*`),
  `backend/Core/Pilotage/DashboardController.cs`, `ConsoleController.cs`,
  `frontend/src/modules/service-configuration-management/`,
  `frontend/src/core/pages/reporting/ConfigurationTab.jsx`, `RecordForm.jsx`, `Layout.jsx`
  (sous-entrée active : préfixe le plus long), `demo/donnees/charger.py` (CI de démonstration
  complétés pour CFG-43 et CFG-44) ; tests `DiscoveryTests`, `DiscoveryUnitTests`,
  `CmdbInventoryTests`, `Cmdb.test.jsx` (217 tests d'API, 94 tests d'interface).
- **Documentation** : pratique Configuration (statuts ✅, § 2, 3, 4.2, 5, 8, 9, 10),
  reporting (§ 8, REP-07, REP-50 à REP-53), frontend (routes, navigation, paramétrage,
  champs conditionnels), exploitation (section `Discovery`, § Découverte du réseau),
  architecture, base de données, sécurité, produit, glossaire (actif inconnu), README,
  journal des versions (Ajouté, Mise à jour), plan d'action (phases F13)
- **Recette sur l'AMD** : migration appliquée sans erreur, clé du coffre en secret Kubernetes ;
  24 contrôles par l'API (coffre, droits, portefeuille, matériel, inventaire, tableau de bord,
  validation des tâches, balayage manuel de 192.168.1.0/28 autorisé par le mainteneur :
  3 équipements en 9 s, sas, ignorer et rétablir, création du CI depuis le sas, console), puis
  nettoyage complet. Défaut trouvé et corrigé : depuis un pod, le DNS inverse renvoie un nom
  synthétique du cluster (« 192-168-1-11.kubernetes.default.svc.cluster.local ») ; un tel nom
  n'est plus retenu comme nom d'hôte (`NetworkScanner.UsefulHostname`).
- **Incident** : le scratchpad a été vidé pendant la préparation de la fusion ; le correctif
  non poussé a été refait depuis la branche distante.
- **Reste à faire** : SNMP v3, SSH, WinRM, hyperviseurs, cartographie des dépendances, agent
  nomade, preuves NIS 2 dans l'évaluation ; captures d'écran de la configuration à
  régénérer.
- **Commit** : PR « CMDB augmentée et découverte automatique » (branche `cmdb-decouverte`)

## Jeton de session en cookie HttpOnly, CSP (S5)

- **Quoi** : l'API pose le jeton dans un cookie `saloha_session` (`HttpOnly`,
  `SameSite=Strict`, `/api`, `Secure` en HTTPS via `X-Forwarded-Proto`) ; `GET /api/auth/me`,
  `POST /api/auth/logout` ; garde CSRF (`X-S-Aloha: 1` exigé sur une modification portée par le
  cookie) ; jeton dans la réponse seulement sur `returnToken` (scripts). Connexion découplée
  de LDAP (`IAuthenticator`). Frontend sans jeton : profil seul, session reprise par `/me`,
  déconnexion serveur. nginx : CSP (empreinte du script de thème vérifiée par un test),
  `nosniff`, `Referrer-Policy`, `X-Forwarded-Proto`.
- **Pourquoi** : décision S5 du 2026-10-19 ([ADR-0018](../decisions/adr-0018-jeton-en-cookie-httponly-et-csp.md),
  précisé pour les scripts).
- **Fichiers** : `backend/Core/Auth/AuthController.cs`, `SessionCookie.cs`, `IUserDirectory.cs`,
  `Program.cs`, `frontend/src/api.js`, `App.jsx`, `Login.jsx`, `Layout.jsx`, `nginx.conf`,
  `demo/donnees/charger.py` ; tests `SessionCookieTests`, `FakeAuthenticator`, `csp.test.js`
- **Documentation** : architecture, sécurité, frontend, exploitation (§ Session et HTTPS),
  ADR-0018, journal des versions. Soldé du plan d'action : S5.
- **À la recette AMD** : connexion, rechargement, nouvel onglet, déconnexion ; aucune
  violation CSP dans la console du navigateur ; scripts locaux de données de test à passer à
  `returnToken`.
- **Commit** : PR « Jeton de session en cookie HttpOnly, CSP (S5) »
